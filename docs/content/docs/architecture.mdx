Shield is organized as a set of focused Go packages. The `engine` package is the central coordinator. The other packages define the entities, store interfaces and plugins that compose around it.

The six evaluation layers are the design, not the current behaviour. `executeScan` has a placeholder for each layer and runs none of them, so every scan returns `allow` with no findings. `engine.Capabilities()` reports `Evaluation: false` and lists all six layers as unavailable.

## Layered safety model

```
┌──────────────────────────────────────────────────────────────────┐
│                        engine.Engine                              │
│  ScanInput / ScanOutput / Capabilities / Health / Stop            │
├──────────────────────────────────────────────────────────────────┤
│              Six cognitive safety layers (not implemented)        │
│                                                                    │
│  Layer 1: INSTINCTS    (<10ms)   Injection, Jailbreak, Exfil     │
│  Layer 2: AWARENESS    (<50ms)   PII, Topic, Intent, Sentiment   │
│  Layer 3: BOUNDARIES   (<5ms)    Hard topic/action/data limits   │
│  Layer 4: VALUES       (<100ms)  Toxicity, Brand, Honesty        │
│  Layer 5: JUDGMENT     (<500ms)  Grounding, Relevance, Compliance│
│  Layer 6: REFLEXES     (<10ms)   Custom condition→action rules   │
│                                                                    │
│  Planned: a high-confidence instinct hit skips deeper layers.     │
├──────────────────────┬───────────────────────────────────────────┤
│  plugin.Registry      │  SafetyProfile composition                │
│  OnScanStarted        │  Instincts + Awareness + Boundaries +    │
│  OnScanCompleted      │  Values + Judgment + Reflexes             │
│  OnShutdown           │  → compose into named profiles           │
│  (15 hook interfaces) │  (stored, not yet evaluated)              │
├──────────────────────┴───────────────────────────────────────────┤
│                        store.Store                                │
│  (composite: scan.Store + instinct.Store + awareness.Store +      │
│   boundary.Store + values.Store + judgment.Store + reflex.Store +  │

│   Migrate/Ping/Close)                                             │
└──────────────────────────────────────────────────────────────────┘
```

## Engine construction

`engine.New` accepts option functions. It never returns an error today, but check it anyway.

```go
eng, err := engine.New(
    engine.WithStore(pgStore),           // optional: composite Store
    engine.WithConfig(shield.Config{     // optional: stored, not read yet
        EnableShortCircuit: true,
        ScanConcurrency:    10,
    }),
    engine.WithPlugin(metricsPlugin),    // optional: lifecycle hooks
    engine.WithLogger(logger),           // optional: a go-utils log.Logger
)
```

`WithLogger` takes a `log.Logger` from `github.com/xraph/go-utils/log`, not a `*slog.Logger`.

## Scan execution flow

What `ScanInput` and `ScanOutput` do today:

1. Set the direction (`input` or `output`) and create a `scan_` ID.
2. Build a `scan.Result` with decision `allow`, stamped with the tenant and app from the context.
3. Emit `OnScanStarted`.
4. Skip the six layers (they're placeholders).
5. Emit `OnScanCompleted`, and `OnScanBlocked` if the result is blocked (it never is yet).
6. Persist the result with `CreateScan` when a store is set. A persistence error is logged as a warning and the scan still returns successfully.

The layers, once implemented, are meant to run in this order:

1. **Instincts.** Pre-conscious, immediate threat detection: prompt injection, jailbreak attempts and data exfiltration. Fastest layer, and able to short-circuit the rest.

2. **Awareness.** Perception: PII detection, topic classification, sentiment, intent and language. Produces findings that inform later layers.

3. **Boundaries.** Hard binary limits. Topics, actions or data patterns that are forbidden outright, with no thresholds.

4. **Values.** Ethical evaluation: toxicity, brand safety, honesty and respect, with thresholds and severity levels.

5. **Judgment.** Contextual risk assessment: grounding (hallucination detection), relevance, consistency and compliance. The slowest layer, and it needs context.

6. **Reflexes.** Condition-action rules: rate limiting, escalation, pattern triggers and custom rules. The final layer before a decision.

## Tenant isolation

`shield.WithTenant(ctx, id)` and `shield.WithApp(ctx, id)` put identifiers on the context. Today only the engine reads them, to stamp `TenantID` and `AppID` on each scan result.

The subsystem stores (`store.Store`) don't read the context. Lookups by ID, such as `GetScan` or `GetInstinct`, return the row whatever its tenant or app, and `List*` methods filter only by the `AppID` and `TenantID` you put in the filter. An empty filter returns every row. Scope those calls yourself.

The dashboard path is stricter. The `store.DashboardStore` methods take a `store.Scope`, refuse an empty tenant or app with `store.ErrScope`, and never widen a query to every row. The dashboard contributor builds that scope from the signed-in user's claims, never from request parameters. See [Multi-tenancy](/docs/concepts/multi-tenancy).

## Plugin system

Plugins implement the `plugin.Plugin` base interface (just `Name() string`) and opt in to specific lifecycle hooks by implementing more interfaces:

```go
type Plugin interface {
    Name() string
}

// Opt-in hooks (implement any subset):
type ScanStarted interface {
    OnScanStarted(ctx context.Context, scanID id.ScanID, direction string, text string) error
}
type ScanCompleted interface { /* ... */ }
type InstinctTriggered interface { /* ... */ }
type BoundaryEnforced interface { /* ... */ }
// ... 15 hook interfaces in total
```

`plugin.Registry` type-caches plugins at registration time, so emit calls iterate only over plugins that implement the relevant hook. Hook errors never reach the scan. The engine builds its registry with a no-op logger, so those errors are dropped silently.

Only `OnScanStarted`, `OnScanCompleted` and `OnShutdown` are emitted today. The other twelve hooks are defined and the built-in plugins implement them, but nothing calls them yet.

Built-in plugins:
- `observability.MetricsExtension`: 14 counters, one per hook except shutdown
- `audithook.Extension` (import path `audit_hook`): bridges lifecycle events to an audit trail backend
