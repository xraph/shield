Shield is organized as a set of focused Go packages. The `engine` package is the central coordinator: it loads a tenant's safety profile from the store, runs it, and records the scan. The other packages define the entities, the detectors, the store interfaces and the plugins that compose around it.

## Layered safety model

```
┌──────────────────────────────────────────────────────────────────┐
│                        engine.Engine                             │
│  ScanInput / ScanOutput / ScanToolCall / Capabilities / Health   │
├──────────────────────────────────────────────────────────────────┤
│  resolve profile (tenant, app, name), cached for ProfileCacheTTL │
├──────────────────────────────────────────────────────────────────┤
│  Layer 1: INSTINCTS   injection, jailbreak, exfiltration,        │
│                       manipulation (instinct/detection)          │
│  Layer 2: AWARENESS   PII, secrets, topics (awareness/perception)│
│  Layer 3: BOUNDARIES  topic, data, output and action limits      │
│  Layer 4: VALUES      safety and toxicity lexicons               │
│                       (values/principles)                        │
│  Layer 5: JUDGMENT    scores over findings, optional model judge │
│  Layer 6: REFLEXES    condition and action rules                 │
│  then:    POLICIES    the tenant's org and assigned app policies │
│                                                                  │
│  A block ends the scan after its layer (EnableShortCircuit).     │
├──────────────────────┬───────────────────────────────────────────┤
│  plugin.Registry     │  SafetyProfile composition                │
│  15 hook interfaces, │  Instincts + Awareness + Boundaries +     │
│  all emitted         │  Values + Judgment + Reflexes             │
├──────────────────────┴───────────────────────────────────────────┤
│                        store.Store                               │
│  the eleven subsystem stores + Migrate / Ping / Close,           │
│  every call scoped to a tenant                                   │
└──────────────────────────────────────────────────────────────────┘
```

## Engine construction

`engine.New` accepts option functions. It never returns an error today, but check it anyway.

```go
eng, err := engine.New(
    engine.WithStore(pgStore),           // required for scans: profiles live in the store
    engine.WithConfig(cfg),              // optional: a shield.Config, see Configuration
    engine.WithPlugin(auditPlugin),      // optional: lifecycle hooks
    engine.WithJudge(judge),             // optional: the model judge, used only with cfg.ModelJudge
    engine.WithLogger(logger),           // optional: a go-utils log.Logger
    engine.WithMetrics(metrics),         // optional: a go-utils metrics.Metrics
)
```

`WithLogger` takes a `log.Logger` from `github.com/xraph/go-utils/log`, not a `*slog.Logger`. Without `WithStore` the engine still builds, but every scan returns `shield.ErrNoStore`.

## Scan execution flow

What `ScanInput`, `ScanOutput` and `ScanToolCall` do:

1. Set the direction (`input`, `output` or `tool_call`) and create a `scan_` ID. A tool call's arguments are checked and split into units first.
2. Check the tenant on the context, the size limit and the store.
3. Emit `OnScanStarted`, then resolve the profile named by the input or by `Config.DefaultProfile`. A failure in this step or the one before returns an error, emits `OnScanFailed` and stores nothing. A scan that fails a check in step 2 never reaches `OnScanStarted`, so no plugin sees its text.
4. Emit `OnSafetyProfileResolved`, then run the six layers and the tenant's policies, each under its own `evaluate layer` span. Each layer emits its own hooks as it finds things. With `EnableShortCircuit` a block stops the run after its layer.
5. Fold the findings into one decision, the strictest, and build `Redacted`.
6. Emit `OnScanCompleted`, and `OnScanBlocked` if the result is blocked.
7. Persist the result with `CreateScan`. A persistence error is logged as a warning, marks the span failed, and the scan still returns its verdict.

Every step runs under one `scan content` span, so profile resolution, the layers, the judge, the plugin hooks and the store write show up as its children. When the scan returns, the engine counts it on `shield_scans_completed_total` and records its wall time on `shield_scan_duration_seconds`. See [Observability](/docs/guides/observability).

[Evaluation](/docs/concepts/evaluation) covers what each layer matches, how actions map to decisions, and the tool-call rules.

## Tenant isolation

`shield.WithTenant(ctx, id)` and `shield.WithApp(ctx, id)` put identifiers on the context, and every engine-facing call needs the tenant. A scan without one returns `shield.ErrTenantRequired`, and so does every `store.Store` read and write, unless a list filter carries `TenantID` itself.

Inside a tenant, a row of another tenant is invisible: a get by its ID returns not-found, an update returns not-found, and a delete does nothing. A filter whose `TenantID` differs from the context's is `shield.ErrTenantMismatch`. Names are unique per app and tenant.

The dashboard path takes its scope from `store.Scope` instead. The `store.DashboardStore` methods refuse an empty tenant or app with `store.ErrScope`, and the dashboard contributor builds that scope from the signed-in user's claims, never from request parameters. See [Multi-tenancy](/docs/concepts/multi-tenancy) for the full rules, policies included.

## Plugin system

Plugins implement the `plugin.Plugin` base interface (just `Name() string`) and opt in to specific lifecycle hooks by implementing more interfaces:

```go
type Plugin interface {
    Name() string
}

// Opt-in hooks (implement any subset):
type ScanStarted interface {
    OnScanStarted(ctx context.Context, scanID id.ScanID, direction string, text string) error
}
type ScanCompleted interface { /* ... */ }
type InstinctTriggered interface { /* ... */ }
type BoundaryEnforced interface { /* ... */ }
// ... 15 hook interfaces in total
```

`plugin.Registry` type-caches plugins at registration time, so emit calls iterate only over plugins that implement the relevant hook. Hook errors never reach the scan. The registry logs them on the engine's logger, counts them on `shield_plugin_hooks_failed_total` and marks the `run plugin hooks` span failed.

The engine emits all 15 hooks. See [Custom plugins](/docs/guides/custom-plugin) for when each one fires.

Built-in plugin:
- `audithook.Extension` (import path `audit_hook`): bridges lifecycle events to an audit trail backend

`observability.MetricsExtension` is deprecated and does nothing. The engine records its own metrics through `engine.WithMetrics`; see [Observability](/docs/guides/observability).
