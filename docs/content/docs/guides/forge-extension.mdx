---
title: Forge Extension
description: Mount Shield into a Forge application as an extension with lifecycle management.
---

Shield ships a Forge extension in the `extension` package. It reads `extensions.shield` (or `shield`) from your config, takes its store from a `*grove.DB` in the container, provides `*engine.Engine`, runs migrations on start and registers the `shield` dashboard contributor.

Scans through the extension's engine behave like any other: they need a tenant on the context and a profile in the store. See [Getting started](/docs/getting-started) and [Evaluation](/docs/concepts/evaluation).

## Installation

```go
import shieldext "github.com/xraph/shield/extension"
```

## Registering the extension

```go
package main

import (
    "log"

    "github.com/xraph/forge"
    shieldext "github.com/xraph/shield/extension"
)

func main() {
    app := forge.NewApp(forge.AppConfig{
        Name:        "safety",
        HTTPAddress: ":8080",
        Extensions: []forge.Extension{
            shieldext.New(),
        },
    })

    if err := app.Run(); err != nil {
        log.Fatal(err)
    }
}
```

You can also call `app.RegisterExtension(shieldext.New(...))` before `Run`.

Other code resolves the engine from the container by type:

```go
eng, err := forge.Inject[*engine.Engine](app.Container())
```

## What the extension does

| Lifecycle event | Behaviour |
|----------------|-----------|
| `Register` | Loads config, resolves the store (see below), builds the engine and provides `*engine.Engine` in the DI container |
| `Start` | Runs `Migrate` on the store unless migrations are disabled or there's no store |
| `Stop` | Calls `engine.Stop`, which emits `OnShutdown` to plugins |
| `Health` | Pings the store. With no store it returns `shield: persistence is not configured` |

Shield mounts no REST routes of its own. Its only HTTP surface is the dashboard contract, which Forge's dashboard extension serves (see [Dashboard contract](/docs/api-reference/http-api)).

## Extension options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `WithStore(s)` | `store.Store` | none | Composite store. A grove store resolved in `Register` replaces it (see below) |
| `WithGroveDatabase(name)` | `string` | not set | Resolve a `*grove.DB` from DI; `""` means the default one |
| `WithPlugin(p)` | `plugin.Plugin` | none | Lifecycle plugin (repeatable) |
| `WithEngineOption(opt)` | `engine.Option` | none | Pass any engine option through, such as `engine.WithJudge(j)` for the model judge |
| `WithConfig(cfg)` | `Config` | `DefaultConfig()` | Replace the whole config struct |
| `WithDisableRoutes()` | none | `false` | Don't register the dashboard contributor |
| `WithDisableMigrate()` | none | `false` | Skip migrations on `Start` |
| `WithBasePath(path)` | `string` | `""` | Stored in config but not used by anything |
| `WithRequireConfig(b)` | `bool` | `false` | Fail `Register` when neither `extensions.shield` nor `shield` is in your config |
| `WithDashboardActorResolver(fn)` | `contract.ActorResolver` | claims resolver | Map the dashboard principal to a Shield scope and permissions |
| `WithDashboardAudit(fn)` | `admin.Audit` | none | Audit sink; PII retention commands refuse to run without it |

## File-based configuration (YAML)

The extension looks for config under these keys, in order:

1. `extensions.shield`
2. `shield`

```yaml
extensions:
  shield:
    disable_routes: false
    disable_migrate: false
    grove_database: ""
    default_profile: ""
    enable_short_circuit: true
    max_scan_bytes: 1048576
    profile_cache_ttl: 30s
    store_redacted: false
    model_judge: false
    judge_timeout: 5s
    judge_concurrency: 8
    scan_concurrency: 10
    shutdown_timeout: 30s
    base_path: ""
```

| YAML key | Type | Default | What it does |
|----------|------|---------|-------------|
| `disable_routes` | `bool` | `false` | `true` stops the dashboard contributor from registering |
| `disable_migrate` | `bool` | `false` | `true` skips `Migrate` on `Start` |
| `grove_database` | `string` | `""` | Name of a `*grove.DB` in the container. A non-empty value turns on grove resolution |
| `default_profile` | `string` | `""` | The profile a scan runs when it names none |
| `enable_short_circuit` | `bool` | `true` | A block ends the scan after the layer that found it |
| `max_scan_bytes` | `int` | `1048576` | The largest scan, in bytes. Larger ones fail with `shield.ErrInputTooLarge` |
| `profile_cache_ttl` | `duration` | `30s` | How long a compiled profile is reused. Negative turns the cache off |
| `store_redacted` | `bool` | `false` | Keep the redacted text on stored scans |
| `model_judge` | `bool` | `false` | Let the `model` assessor call the judge you pass with `WithEngineOption(engine.WithJudge(j))` |
| `judge_timeout` | `duration` | `5s` | The bound on one judge call |
| `judge_concurrency` | `int` | `8` | Judge calls in flight across the engine |
| `scan_concurrency` | `int` | `10` | Copied into the engine config. Nothing reads it yet |
| `shutdown_timeout` | `duration` | `30s` | Copied into the engine config. Nothing reads it yet |
| `base_path` | `string` | `""` | Read and logged. Nothing uses it |

The dashboard's `config.detail` query shows the effective values. [Configuration](/docs/concepts/configuration) has the details of each engine setting.

### Merge behaviour

When a config file is found, it's merged with your programmatic options. `DisableRoutes`, `DisableMigrate`, `EnableShortCircuit`, `StoreRedacted` and `ModelJudge` set to `true` in code always win. For the string, duration and int fields, the file wins and code fills the gaps, then defaults fill what's left. Since the programmatic default for `EnableShortCircuit` is `true`, setting `enable_short_circuit: false` in YAML has no effect.

When no config file is found, the programmatic config is used with defaults filled in. `WithRequireConfig(true)` turns that case into an error:

```go
ext := shieldext.New(
    shieldext.WithRequireConfig(true),
)
```

## Store resolution

`Register` picks the store like this:

1. If you called `WithGroveDatabase(name)` or set `grove_database`, it resolves that `*grove.DB` (the default one for `""`) and fails if it isn't in the container.
2. Otherwise, if the container has a default `*grove.DB`, it uses that.
3. Otherwise it uses the store from `WithStore`, if you passed one.
4. Otherwise the engine runs with no store: every scan returns `shield.ErrNoStore`, migrations are skipped and `Health` reports an error.

For a grove database, the store is picked from the driver name: `pg` gives `store/postgres`, `sqlite` gives `store/sqlite` and `mongo` gives `store/mongo`. Any other driver is an error. You don't import the store packages yourself.

Steps 1 and 2 win over `WithStore`. If the container has a `*grove.DB` (for example from grove's Forge extension), a store you pass with `WithStore` is replaced by one built from that database.

```go
ext := shieldext.New(
    shieldext.WithGroveDatabase("shield"), // a named grove.DB
)
```

## Dashboard

The extension implements Forge's dashboard contributor interface and registers the `shield` contributor when the dashboard extension is present and `disable_routes` is false. Registration needs a store that implements `store.DashboardStore`, which all three built-in stores do. With no store, registration fails.

The default resolver takes scope only from the signed-in user's claims, never from request parameters:

| Claim | Type | Meaning |
|-------|------|---------|
| `tenant_id` | non-empty string | Tenant scope. If `shield_tenant_id` is also set, it must match |
| `app_id` | non-empty string | App scope. If `shield_app_id` is also set, it must match |
| `shield_read` | `true` | Required for every query and command |
| `shield_manage` | `true` | Required for commands (create, update, delete, enable, assign) |
| `shield_privacy_manage` | `true` | Required, with `shield_manage`, for PII retention commands |

PII retention also needs an audit sink from `WithDashboardAudit`. Without one, those commands return `UNAVAILABLE`. If your claims look different, pass your own resolver with `WithDashboardActorResolver`. It must authenticate the principal and authorize every scope and permission it returns.

### Tenant actors and the app scope

The default resolver builds a tenant actor, and a tenant actor manages only its own tenant's policies:

- A policy it creates is org-level, keyed by its tenant (`scope_level: org`, `scope_key` = the tenant).
- It sees its own org-level policies plus the app-level policies assigned to it, and those are read-only. Editing or deleting one returns `PERMISSION_DENIED`.
- It can't assign or unassign policies.
- It reads only its own tenant's compliance reports.

App-level policies belong to the operator of the app, because every tenant of the app shares them. To act as that operator, your resolver grants the app scope, which nothing in a request can set:

```go
shieldext.WithDashboardActorResolver(func(ctx context.Context, p dash.Principal) (admin.Actor, error) {
    a, err := shieldcontract.ResolveActor(ctx, p)
    if err != nil {
        return admin.Actor{}, err
    }
    if isAppOperator(p) { // your own check
        a.Scope.PolicyLevel = "app"
        a.Scope.PolicyKey = a.Scope.AppID // must equal AppID
    }
    return a, nil
})
```

An actor with that scope creates, edits and deletes app-level policies, assigns them to the tenant in its scope, and reads app-level compliance reports. Its writes drop every tenant's cached profiles, since any of them may have the policy assigned. Outside the dashboard, a `store.Store` call with no tenant on the context is an operator call too.

## Metrics and tracing

There's nothing to add. `Register` hands the engine your app's metrics and logger, so scan and plugin-hook metrics show up on `/_/metrics` as `forge_shield_scans_completed_total`, `forge_shield_scan_duration_seconds` and `forge_shield_plugin_hooks_failed_total`. Scans, plugin hooks and PII purges are traced on the provider `forge.New` installs, under whatever span called them. The [observability guide](/docs/guides/observability) lists every span, attribute, metric and label.

To turn the metrics off, pass a nil sink through to the engine:

```go
shieldext.New(shieldext.WithEngineOption(engine.WithMetrics(nil)))
```

## Adding audit trails

The audit hook plugin sends lifecycle events to any `audithook.Recorder`, such as an adapter for [Chronicle](https://github.com/xraph/chronicle):

```go
import audithook "github.com/xraph/shield/audit_hook"

auditPlugin := audithook.New(myRecorder,
    audithook.WithActions(
        audithook.ActionScanBlocked,
        audithook.ActionInstinctTriggered,
        audithook.ActionPIIDetected,
    ),
)

ext := shieldext.New(
    shieldext.WithPlugin(auditPlugin),
)
```

All three fire: a blocked scan, an instinct that fired, and PII an awareness detector found.
