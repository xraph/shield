---
title: Multi-Tenancy
description: How Shield scopes scans, policies and safety entities to apps and tenants, and where you have to do it yourself.
---

Shield entities carry an **app** ID (logical application boundary) and a **tenant** ID (user or organization boundary). How strictly that's enforced depends on which API you call. The engine stamps scope from the context, the plain `store.Store` methods filter only by the IDs you hand them, and the dashboard store contract refuses to run without a scope.

## Context injection

Put scope on the Go context with helpers from the root `shield` package:

```go
import "github.com/xraph/shield"

ctx = shield.WithTenant(ctx, "org-123")
ctx = shield.WithApp(ctx, "myapp")
```

## Extraction

Read it back from any context:

```go
tenantID := shield.TenantFromContext(ctx) // "org-123"
appID    := shield.AppFromContext(ctx)    // "myapp"
```

Both return an empty string if no value is set.

## AppID vs TenantID

| Scope | Where it lives | Example |
|-------|---------|---------|
| **AppID** | A field on instincts, awareness, boundaries, values, judgments, reflexes, profiles and scans. Names are unique per app. | `"myapp"`, `"staging"` |
| **TenantID** | A field on the same rows plus PII tokens. It defaults to empty on the safety primitives and profiles. | `"org-123"`, `"user-456"` |

Policies use `ScopeKey` and `ScopeLevel` (`app` or `org`) instead, with names unique per scope key, and you assign them to tenants with `AssignToTenant`.

## What the engine does

`ScanInput` and `ScanOutput` read the tenant and app from the context and write them onto the `scan.Result` they persist. A scan on a context without them is stored with empty IDs.

## What `store.Store` does

The subsystem store methods don't read the context at all:

- `Get<Thing>(ctx, id)` looks a row up by ID only, whatever its tenant or app. `GetScan` returns another tenant's scan if you pass its ID.
- `Get<Thing>ByName(ctx, appID, name)` filters by the app ID you pass.
- `List*` methods filter by the `AppID` and `TenantID` fields you set on the filter. Leave them empty (or pass a `nil` filter) and you get every row.
- PII methods such as `DeletePIITokensByTenant` and `PIIStats` take the tenant ID as an argument.

So if your own code serves Shield data to callers, take the tenant and app from your auth layer and pass them into every filter and name lookup, and check the `TenantID` and `AppID` on rows you fetch by ID.

```go
tenantID := shield.TenantFromContext(ctx)
appID := shield.AppFromContext(ctx)

scans, err := eng.Store().ListScans(ctx, &scan.ListFilter{
    AppID:    appID,
    TenantID: tenantID,
    Limit:    20,
})
```

## What the dashboard does

The Forge dashboard contributor goes through a stricter contract, `store.DashboardStore`. Every call takes a `store.Scope{TenantID, AppID}`. An empty tenant or app fails with `store.ErrScope` and is never widened to every row, and a row outside the scope reads as `store.ErrNotFound`. The default resolver builds that scope from the signed-in user's `tenant_id` and `app_id` claims, never from request parameters. See the [Forge extension guide](/docs/guides/forge-extension#dashboard).

## Example: two tenants

```go
// Tenant 1 scans content.
ctx1 := shield.WithApp(context.Background(), "myapp")
ctx1 = shield.WithTenant(ctx1, "tenant-1")
result1, _ := eng.ScanInput(ctx1, &scan.Input{Text: "hello"})

// Tenant 2 scans content.
ctx2 := shield.WithApp(context.Background(), "myapp")
ctx2 = shield.WithTenant(ctx2, "tenant-2")
result2, _ := eng.ScanInput(ctx2, &scan.Input{Text: "hello"})

// result1.TenantID is "tenant-1" and result2.TenantID is "tenant-2".
// To list only tenant 1's history, filter on it:
history, _ := eng.Store().ListScans(ctx1, &scan.ListFilter{AppID: "myapp", TenantID: "tenant-1"})
```
