Shield is a Go library that checks what goes into and comes out of an LLM app or AI agent. You describe **Instincts**, **Awareness**, **Boundaries**, **Values**, **Judgment** and **Reflexes**, compose them into safety profiles and policies, store them per tenant and app in PostgreSQL, SQLite or MongoDB, and scan text and tool calls against them.

Shield is a library, not a service. You bring your own LLM provider, database and HTTP server.

## What a scan does

`ScanInput`, `ScanOutput` and `ScanToolCall` run the tenant's safety profile through six layers, then the tenant's policies, and return a decision: `allow`, `flag`, `redact` or `block`, plus `require_approval` for tool calls. Detection is deterministic: a prompt-injection corpus, PII and secret detectors with validators and entropy checks, lexicons for destructive commands and abuse, and your own patterns. A model judge is optional, off by default, and can only raise risk. [Evaluation](/docs/concepts/evaluation) walks through every layer.

## The human safety model

Shield models AI safety the way you would describe human cognition.

| Layer | What it represents | What runs | Go package |
|-------|-------------------|-------|------------|
| **Instincts** | Pre-conscious threat detection (flinch response) | Injection, jailbreak, exfiltration and manipulation patterns, hidden and encoded text, canary tokens | `instinct` |
| **Awareness** | Perception: what you notice | PII and secret detectors, topic and custom patterns | `awareness` |
| **Boundaries** | Hard limits that cannot be crossed | Topic, data, output and tool-call deny and allow lists | `boundary` |
| **Values** | Ethical evaluation | Destructive-command and toxicity lexicons, your own terms and patterns | `values` |
| **Judgment** | Contextual risk assessment | Scores over the findings so far, and the optional model judge | `judgment` |
| **Reflexes** | Trained condition-action responses | Pattern, finding, score, context and rate triggers | `reflex` |

## What it does

- Scans text going into a model, text going out, and tool calls an agent proposes, against a safety profile stored per tenant.
- Quotes untrusted text (a build log, an issue body) so a model reads it as data, with injected instructions removed line by line.
- Redacts PII and secrets with numbered placeholders such as `[EMAIL_1]`.
- Ships `presets.InfraAgent`, a ready-made bundle for an infrastructure agent, and `redteam`, the injection fixtures Shield is tested against. See [Agent safety](/docs/guides/agent-safety).
- Puts Shield behind [nexus](https://github.com/xraph/nexus) guards with the separate `integrations/nexusguard` module. See [Nexus guard](/docs/guides/nexus-guard).
- Requires a tenant on every scan and every store call, so one tenant never reads another's rows. Names are unique per app and tenant.
- Policies with ordered rules: org-level policies a tenant owns, and app-level policies an operator assigns to tenants.
- A scan record for every scan, with direction, decision, findings, PII count, profile, policies, tenant and app.
- A PII token store (placeholder, type, an encrypted value you supply, expiry) with per-tenant deletion and age-based purge. Shield redacts PII but doesn't encrypt or vault it.
- Compliance report records for the EU AI Act, NIST AI RMF and SOC 2. Shield stores reports; it doesn't generate them.
- 15 lifecycle hooks for plugins, all of which fire, and an audit plugin.
- OpenTelemetry spans for scans, layers, the judge, plugin hooks and PII purges, and scan and hook metrics that a Forge app scrapes on `/_/metrics`. See [Observability](/docs/guides/observability).
- A `forge.Extension` that provides `*engine.Engine` in the DI container, runs migrations and registers an authenticated dashboard contributor.

## Design philosophy

Shield is a set of Go packages you import, not a service. You control `main`, the database connection and the process lifecycle.

Detection comes first from deterministic code you can read and test, and a decision never needs a model. The primitives are named after human cognition (instincts, awareness, boundaries, values, judgment and reflexes), so the configuration reads the way you'd describe the rules out loud.

Every subsystem defines a Go interface, and `store.Store` composes them, so you swap the backend by passing a different store. All entities use type-prefixed, K-sortable, UUIDv7-based identifiers (`scan_`, `pol_`, `inst_`, `jdg_`, `sprf_` and so on).

## Quick look

```go
ctx := shield.WithTenant(context.Background(), "acme")
ctx = shield.WithApp(ctx, "support-bot")

// st is a store with a "customer-facing" profile for acme; see Getting started.
eng, err := engine.New(engine.WithStore(st))
if err != nil {
    log.Fatal(err)
}

result, err := eng.ScanOutput(ctx, &scan.Input{
    Text:    "Sure, I've emailed jane@example.com with the details.",
    Profile: "customer-facing",
})
if err != nil {
    log.Fatal(err) // a scan error means you don't know: treat it as a block
}

log.Printf("Decision: %s", result.Decision) // redact
log.Printf("Send: %s", result.Redacted)     // Sure, I've emailed [EMAIL_1] with the details.
```
